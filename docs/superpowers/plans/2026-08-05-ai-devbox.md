# AI Devbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a persistent, hardened `ai-dev` SSH environment to the NAS Compose application and expose it exclusively through a separately authorized Tailscale Service.

**Architecture:** A focused included Compose model builds an Ubuntu 24.04 development image whose main workload is root-started OpenSSH but whose sessions are always the unprivileged `ai-dev` user. A read-only image is paired with explicit bind-mounted state and bounded tmpfs mounts. The existing Tailscale gateway adds a raw TCP Service to `ai-devbox:22`; the devbox publishes no host port and shares no control-plane private network.

**Tech Stack:** Ubuntu 24.04, OpenSSH, Docker Compose include, Bash entrypoint, Node.js 22, Python 3, `uv`, Rust, tmux, pytest structural tests, shell/container integration tests.

## Global Constraints

- The devbox is part of the one `deploy/compose` project and starts with normal `docker compose up -d`.
- Only `ai-dev` may log in; root, passwords, keyboard-interactive login, sudo, forwarding, tunnels, and user environment injection are disabled.
- Do not mount the Docker socket, host devices, or control-plane private networks.
- Use a read-only root filesystem and bounded tmpfs mounts for `/run`, `/tmp`, and `/var/tmp`.
- Retain `no-new-privileges`; do not start with `cap_drop: ALL`.
- Persist home, workspaces, caches, and SSH host keys under one configurable NAS data root.
- Never commit a real authorized key, credential, LAN address, or tailnet identity.
- Image-provided tools must remain available when an empty persistent home hides `/home/ai-dev`.
- Never recursively chown an existing workspace during startup.
