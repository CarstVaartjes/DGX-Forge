# Temporary Local Release Workaround Design

**Date:** 2026-08-06

**Status:** Approved for specification review

**Scope:** First DGX-Forge platform release only

## Purpose

GitHub Actions was in a major outage while DGX-Forge was preparing its first
real release. Builds remained queued for hours even though Git operations,
Packages, and the GitHub API remained usable. This design keeps deterministic
build and verification work moving locally without weakening the platform's
existing GitHub OIDC, artifact-attestation, or TUF publication boundaries.

This is a temporary incident procedure. It does not create a second permanent
release authority and it does not make a developer token, workstation key, or
NAS administrator an alternative to the protected GitHub release identity.

## Invariants

- The first release remains PR-based. Every repository change needed by
  `v0.1.0` must be reviewed and merged before its final artifacts are built.
- A locally verified PR may be merged with an administrator override only while
  GitHub reports the Actions incident and only after its exact local commands,
  commit SHA, and results are recorded on the PR.
- Final artifacts are built from the exact merged release commit. Candidate
  images built from an earlier commit are not release evidence.
- `0.1.0`, `latest`, and the release commit tag may move while the GitHub release
  remains a draft. They become immutable when the release is published.
- Production installation is forbidden until the host updater has a GitHub
  artifact attestation and the platform manifest has an accepted delegated TUF
  publication receipt.
- GitHub Actions OIDC is not replaced with a personal access token, a long-lived
  repository secret, a TUF private key on the workstation, or an unsigned local
  override.
- The TUF root private key remains offline. The protected publication job holds
  only its existing narrowly delegated authority.
- The delegated platform-authority service must be implemented, deployed, and
  independently accepted before the TUF job runs. That service is a normal
  platform prerequisite, not a temporary local signing path; this workaround
  neither embeds it in CI nor relaxes its OIDC claim checks.
- Workload-package publication remains independent and is outside this
  platform-release workaround.

## Local preparation lane

The administrator workstation performs all deterministic, reproducible work:

1. Run the repository's focused local PR checks against the exact PR head.
2. Record the commit SHA, commands, exit status, and test counts on the PR.
3. Merge the PR through GitHub. An administrator override is incident-only and
   does not authorize merging a failing or unreviewed change.
4. Merge a release PR that:
   - makes the official container workflow match the reviewed multi-architecture
     release contract;
   - adds canonical `release/platform/0.1.0.input.json`;
   - updates release-state and operator documentation;
   - contains no generated private key, token, secret value, or mutable image
     locator.
5. From a clean checkout of the merged release commit, run the focused release
   verification, build and push all three `linux/amd64` and `linux/arm64`
   images, and collect their raw manifests, SBOMs, provenance, and digests.
6. Build the canonical Compose deployment bundle, platform manifest, and
   installable host-updater archive with its checksum.
7. Run the repository's platform-release and supply-chain verifiers against the
   exact generated bytes.

Local generation uses the repository-owned scripts and pinned tools. It must
not substitute hand-written manifests, registry-page digests, mutable Compose
input, or an artifact copied from a different checkout.

## Draft publication lane

The GitHub CLI and Packages API remain data transports, not signing authority.
The workstation may:

- push the final digest-addressed container manifests to the three public GHCR
  repositories;
- create the `v0.1.0` tag at the exact merged release commit;
- create a draft GitHub release for that tag;
- upload the canonical platform manifest, image evidence, deployment-bundle
  descriptor, host-updater archive, checksums, and locally generated
  verification report; and
- cancel superseded queued workflow runs so they cannot consume capacity or
  report obsolete results after service recovery.

The draft release is explicitly non-installable. It must not be announced as a
release, selected by a NAS, added to the `stable` channel, or used as a Spark
update source.

## Actions-only trust lane

After GitHub reports Actions recovery, only two bounded jobs run:

1. **Host-updater attestation:** download the already uploaded archive, verify
   its expected SHA-256 from release evidence, and issue the GitHub/Sigstore
   artifact attestation. This job does not rebuild or alter the archive.
2. **Platform authority publication:** download the already uploaded canonical
   manifest and bundle receipt, verify their expected digests, obtain the
   protected-environment GitHub Actions OIDC token, publish the immutable TUF
   target, and update `stable` last. This job does not build containers, run the
   general test suite, or receive the offline root key.

Both jobs fail closed if an uploaded byte, tag target, commit SHA, image digest,
bundle descriptor, predecessor set, environment claim, or authority receipt
differs from the reviewed release evidence.

The second job remains blocked until the normal delegated platform-authority
service has passed its own deployment and OIDC-policy acceptance. GitHub
Actions recovery is necessary but is not treated as proof that this external
release prerequisite exists.

## Finalization

The release operator verifies the artifact attestation and TUF receipts against
the exact draft assets. Only then may the operator publish the GitHub release.
Publication freezes the following as one release unit:

- Git tag and commit SHA;
- API, worker, and Hermes multi-architecture image indexes;
- image manifests, SBOMs, provenance, and evidence records;
- deployment bundle and descriptor;
- canonical platform manifest and immutable TUF target name;
- host-updater archive, checksum, and GitHub attestation; and
- authority and `stable` channel receipts.

The NAS is installed only from the signed immutable TUF target through
`dgx-control-offline`. Direct production Compose deployment from a checkout or
from the three image tags remains forbidden.

## Failure and recovery

- If a local build or verifier fails, no draft release is created or updated.
- If only some GHCR uploads complete, rebuild from the same clean checkout and
  accept only an exact evidence match; otherwise remove the candidate versions
  before retrying.
- If draft assets differ from local evidence, replace the draft assets before
  any Actions trust job runs. Never sign mismatched bytes.
- If the attestation job fails, leave the release draft and correct the job or
  GitHub incident; do not replace it with a PAT-signed statement.
- If TUF target publication succeeds but the channel update fails, retain the
  immutable target and retry only the byte-identical channel operation.
- If any receipt contradicts the expected target, stop and preserve all
  evidence. Do not repoint `stable`, overwrite an immutable target, or publish
  the GitHub release.
- Superseded queued workflows are cancelled before recovery so they cannot
  consume capacity or attach obsolete results after the local release
  candidate has advanced.

## Verification and acceptance

The workaround is accepted only when evidence proves all of the following:

- every merged PR used either successful required checks or a documented
  incident-only local-equivalent verification;
- the release checkout is clean and its commit equals `v0.1.0`;
- all three public image indexes resolve anonymously and contain exactly
  `linux/amd64` and `linux/arm64` runtime manifests plus accessible SBOM and
  provenance attestations;
- `0.1.0`, `latest`, and the release commit tag resolve to the same index for
  each image;
- the deployment bundle and platform manifest pass the repository verifiers;
- the host-updater checksum and GitHub attestation refer to the exact uploaded
  archive;
- the delegated authority receipt names the exact canonical target digest and
  a positive TUF targets version;
- the delegated authority's deployment and GitHub OIDC policy acceptance pass
  before the publication job is enabled;
- `stable` names that same target and was updated after target publication; and
- the published GitHub release contains the complete evidence set.

## Retirement

This procedure ends when `v0.1.0` is published or the GitHub incident is
resolved before draft preparation completes. Normal protected CI publication
remains the only release path afterward. No temporary credential, alternate
authority, relaxed branch rule, or local signing capability is retained.
