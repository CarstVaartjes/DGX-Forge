# v0.1.0 Release Closure Documentation Design

**Date:** 2026-08-06

**Status:** Approved

## Purpose

Make every remaining `v0.1.0` action discoverable, ordered, assigned to a
role, and explicit about its evidence and stop conditions. An operator must be
able to distinguish an executable repository procedure from a capability that
has not yet been implemented.

## Documentation boundaries

Three operator documents divide the responsibility:

1. `v0.1.0-release-checklist.md` is the sole release-order ledger. It records
   the current state, owner, command or linked procedure, evidence, and stop
   condition for every step from PR checks through installation.
2. `platform-authority-deployment.md` owns the delegated authority boundary.
   It documents the shipped client and HTTP contract, states that no authority
   server is shipped yet, lists the server capabilities that must exist, and
   defines deployment and GitHub OIDC acceptance without inventing a local
   signing path.
3. `physical-release-acceptance.md` owns the six physical gates. It separates
   the three signed update envelopes already understood by the verifier from
   the lifecycle, encryption, and replacement-host evidence for which no
   approved exporter currently exists.

Existing README, deployment, publication, recovery, update, PKI, and onboarding
documents link to these three entry points instead of duplicating the release
order.

## Safety requirements

- Missing tooling is written as a blocker, never represented by a fabricated
  command or hand-edited report.
- Simulated evidence cannot be relabelled as physical evidence.
- The workstation, NAS administrator, personal access token, and GitHub
  package uploader are not platform build or TUF authorities.
- The protected tag workflow remains the only official build path.
- Manual `0.1.0` candidates are deleted only immediately before the official
  tag, after every earlier gate is accepted.
- SSH remains one-time onboarding and explicit recovery only; physical Spark
  update acceptance uses the outbound mTLS agent channel.
- No document contains a site-specific Spark name, address, serial, secret, or
  fleet-size assumption.

## Acceptance

The documentation is accepted when an operator can answer, from one checklist:

- what can be done now;
- what is blocked and why;
- who owns each action;
- which exact command or runbook applies;
- which evidence closes the action;
- which failure requires an immediate stop; and
- which actions are forbidden before the preceding gates pass.

Repository link checks, focused runbook contracts, secret/identity scans, and
the offline supply-chain verifier must remain green before the branch is
pushed.
