# Vonk Forge identity cleanup design

## Goal

Replace the unreleased `dgx-forge` product identity with the canonical
technical name `vonk-forge` throughout the installable repository before
building the source-first NAS deployment path.

## Scope and naming rule

`Vonk Forge` is the product name and `vonk-forge` is the repository, package,
service, and runtime identifier. `DGX Spark` remains valid only when referring
to NVIDIA hardware. It is not used as the product name.

This is a pre-release breaking rename. No compatibility aliases, migration
code, dual environment variables, or legacy service names are retained.
There are no released databases, packages, manifests, or installed hosts to
migrate.

## Required replacements

The cleanup covers source, generated artifacts, fixtures, tests, workflows,
and documentation:

| Legacy form | Canonical form |
| --- | --- |
| `DGX Forge`, `DGX-Forge`, `dgx-forge` | `Vonk Forge`, `Vonk Forge`, `vonk-forge` |
| `dgx_control` | `vonk_control` |
| `dgx_agent` | `vonk_agent` |
| `DGX_*` application settings | `VONK_*` application settings |
| `dgx_forge` evidence/JSON key | `vonk_forge` |
| `application/vnd.dgx-forge.*` | `application/vnd.vonk-forge.*` |
| `https://dgx-forge.*` and `spiffe://dgx-forge.*` | equivalent `vonk-forge` URI |
| `/srv/dgx-forge`, `/opt/dgx-forge` | `/srv/vonk-forge`, `/opt/vonk-forge` |
| `/etc/dgx-forge-*`, `/var/lib/dgx-forge-*`, `/run/dgx-forge-*` | corresponding `/etc/vonk-forge-*`, `/var/lib/vonk-forge-*`, `/run/vonk-forge-*` |
| `dgx-forge-*.service` and sockets | `vonk-forge-*.service` and sockets |
| `dgx-forge-agent` package/binary | `vonk-forge-agent` package/binary |
| `dgx-forge-control` Compose/project name | `vonk-forge-control` |
| `ghcr.io/.../dgx-forge-*` | `ghcr.io/.../vonk-forge-*` |
| `svc:dgx-forge` | `svc:vonk-forge` |

The exact `VONK_*` names are generated by mechanically replacing the
application prefix; names describing hardware, such as `DGX Spark`, are not
changed. Upstream repository URLs, model names, and NVIDIA product names are
preserved when they are external identities rather than Vonk Forge-owned
identifiers.

## Components affected

1. Python package directories, imports, console scripts, project metadata, and
   generated OpenAPI clients.
2. Rust crate metadata, agent protocol names, binaries, systemd units, and
   installer paths.
3. Control API titles, health evidence keys, PKI subjects/SPIFFE IDs, schema
   IDs, media types, and content-addressed manifest fixtures.
4. Docker Compose names, environment variables, internal networks, Tailscale
   service names, Caddy hostnames, registry references, and persistent paths.
5. GitHub Actions, GHCR image names, R2/release documentation, package
   metadata, and repository runbooks.
6. All tests and fixtures, including snapshot-like JSON, shell assertions, and
   generated contract files.

## Data and release policy

No data migration or compatibility reader is added. Existing checked-in
manifests and fixtures are regenerated or rewritten to the new media types,
schema identifiers, and evidence keys. The first agent `.deb` and first NAS
release are produced only after this cleanup lands.

## Verification gates

The cleanup is complete only when:

- `rg -n -i 'dgx[-_ ]forge'` finds no product-owned occurrences outside Git
  metadata and build caches.
- `DGX Spark` occurrences are limited to hardware references and upstream
  sources.
- Python, Rust, web, Compose, contract, and installer tests pass.
- Generated OpenAPI, TypeScript, schema, and lock artifacts are deterministic
  and clean.
- The Compose configuration renders with the new `VONK_*` settings and no
  legacy service, path, image, or hostname remains.
- The resulting source tree is clean and the rename is committed as one
  reviewable change before NAS work begins.

## Follow-on NAS design boundary

The source-first NAS design is deliberately not implemented in this spec. It
will consume the canonical names above and define a single operator path that
checks out the repository, prepares local secrets/configuration, builds the
Vonk Forge images, and starts the Compose control host. The signed `.deb`
publication path remains a separate release workflow and does not require the
NAS to pull platform containers from an external registry.
