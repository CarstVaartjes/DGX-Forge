# Vonk Forge identity cleanup design

## Goal

Replace the unreleased `vonk-forge`/GPU node-oriented product language with the
canonical technical name `vonk-forge` throughout the installable repository
before building the source-first NAS deployment path.

## Scope and naming rule

`Vonk Forge` is the product name and `vonk-forge` is the repository, package,
service, and runtime identifier. Vonk-owned code, configuration, paths, API
schemas, commands, and documentation use generic terms such as `node`,
`GPU host`, `cluster`, and `workload`; they do not use `node` or `vonk`.

Opaque external identities are preserved at integration boundaries: upstream
repository URLs, model names, vendor API values, and raw hardware-reported
strings may contain those terms when changing them would falsify provenance or
break interoperability. They must be clearly treated as external evidence,
not as Vonk Forge identifiers or user-facing product names.

This is a pre-release breaking rename. No compatibility aliases, migration
code, dual environment variables, or legacy service names are retained.
There are no released databases, packages, manifests, or installed hosts to
migrate.

## Required replacements

The cleanup covers source, generated artifacts, fixtures, tests, workflows,
and documentation:

| Legacy form | Canonical form |
| --- | --- |
| `Vonk Forge`, `Vonk Forge`, `vonk-forge` | `Vonk Forge`, `Vonk Forge`, `vonk-forge` |
| `vonk_control` | `vonk_control` |
| `vonk_agent` | `vonk_agent` |
| `vonkctl` | `vonkctl` |
| `cluster_profiles` | `cluster_profiles` |
| `WorkloadRun` / `WorkloadRun profiles` | `WorkloadRun` / `workload profiles` |
| `VONK_*` application settings | `VONK_*` application settings |
| `vonk_forge` evidence/JSON key | `vonk_forge` |
| `application/vnd.vonk-forge.*` | `application/vnd.vonk-forge.*` |
| `https://vonk-forge.*` and `spiffe://vonk-forge.*` | equivalent `vonk-forge` URI |
| `/srv/vonk-forge`, `/opt/vonk-forge` | `/srv/vonk-forge`, `/opt/vonk-forge` |
| `/etc/vonk-forge-*`, `/var/lib/vonk-forge-*`, `/run/vonk-forge-*` | corresponding `/etc/vonk-forge-*`, `/var/lib/vonk-forge-*`, `/run/vonk-forge-*` |
| `vonk-forge-*.service` and sockets | `vonk-forge-*.service` and sockets |
| `vonk-forge-agent` package/binary | `vonk-forge-agent` package/binary |
| `vonk-forge-control` Compose/project name | `vonk-forge-control` |
| `ghcr.io/.../vonk-forge-*` | `ghcr.io/.../vonk-forge-*` |
| `svc:vonk-forge` | `svc:vonk-forge` |

The exact `VONK_*` names are generated by mechanically replacing the
application prefix. User-facing references to a GPU node become a node, GPU host,
or cluster member as appropriate. Upstream repository URLs, model names,
vendor API values, and raw hardware evidence are preserved only as external
identities at explicit integration boundaries.

## Components affected

1. Python package directories, imports, console scripts, project metadata, and
   generated OpenAPI clients, including the `vonkctl` to `vonkctl` rename.
2. Rust crate metadata, agent protocol names, binaries, systemd units, and
   installer paths.
3. Control API titles, health evidence keys, PKI subjects/SPIFFE IDs, schema
   IDs, media types, and content-addressed manifest fixtures.
4. Docker Compose names, environment variables, internal networks, Tailscale
   service names, Caddy hostnames, registry references, and persistent paths.
5. GitHub Actions, GHCR image names, R2/release documentation, package
   metadata, and repository runbooks.
6. All tests and fixtures, including snapshot-like JSON, shell assertions, and
   generated contract files.

## Data and release policy

No data migration or compatibility reader is added. Existing checked-in
manifests and fixtures are regenerated or rewritten to the new media types,
schema identifiers, and evidence keys. The first agent `.deb` and first NAS
release are produced only after this cleanup lands.

## Verification gates

The cleanup is complete only when:

- `rg -n -i 'node|vonk'` finds no Vonk-owned occurrences outside Git metadata,
  build caches, and explicitly documented external-evidence fixtures.
- Every allowed external occurrence is at an integration boundary and is
  labeled as external provenance or raw vendor evidence.
- Python, Rust, web, Compose, contract, and installer tests pass.
- Generated OpenAPI, TypeScript, schema, and lock artifacts are deterministic
  and clean.
- The Compose configuration renders with the new `VONK_*` settings and no
  legacy service, path, image, or hostname remains.
- The resulting source tree is clean and the rename is committed as one
  reviewable change before NAS work begins.

## Follow-on NAS design boundary

The source-first NAS design is deliberately not implemented in this spec. It
will consume the canonical names above and define a single operator path that
checks out the repository, prepares local secrets/configuration, builds the
Vonk Forge images, and starts the Compose control host. The signed `.deb`
publication path remains a separate release workflow and does not require the
NAS to pull platform containers from an external registry.
