# Containerized NAS access and AI devbox design

## Purpose

Run the complete Vonk Forge service-host deployment as one manageable Docker
Compose application on the UGREEN NAS. Human-facing control, inference,
observability, and development access is available only through Tailscale. Vonk Forge
GPU nodes retain a restricted LAN path for outbound agent enrollment, mTLS agent
traffic, and authenticated registry pulls.

The deployment also adds a persistent SSH development environment without
making node identity depend on hard-coded GPU node addresses. A GPU node is identified
by its accepted `spk_` identity and mTLS certificate; its current management IP
is a validated observation.

## Existing context

`deploy/compose/compose.yaml` already defines one external-host control-plane
application containing PostgreSQL, the control API and worker, LiteLLM,
Prometheus, Grafana, Caddy, and a private registry. Model-serving containers run
on the Vonk Forge GPU nodes under `adapters/`; they do not move onto the NAS.

The existing Caddy configuration sends `/v1/*` to `litellm:4000` over the
Compose `ingress` network. LiteLLM joins `cluster-egress` for connections to
accepted GPU node model endpoints. Its checked-in bootstrap configuration has an
empty `model_list`; accepted routes are generated by the control plane. The
production worker writes those generated configurations to a
dedicated volume after reconciliation and refreshes their presence and health
evidence every 60 seconds. LiteLLM consumes that volume read-only and a small
PID 1 supervisor restarts it only after an atomic generation change.

The existing agent design is outbound: a manually bootstrapped GPU node connects
to the control plane rather than accepting routine inbound management
connections. This remains the basis of node presence and discovery.

This design is an incremental improvement to that architecture, not a new or
competing platform. It preserves the existing services, outbound-agent trust
model, Caddy-to-LiteLLM route, and GPU node-hosted runtimes. It adds the
containerized tailnet edge and devbox, makes the human-versus-GPU node ingress
split explicit, and removes exact GPU node addresses as identity or long-lived
configuration.

## Decisions

- The NAS deployment is one Compose project and one operational unit.
- The root `deploy/compose/compose.yaml` is the only normal entry point.
- Focused component definitions may be factored into included Compose files;
  `extends` is reserved for service configuration inheritance.
- Tailscale runs in a dedicated container, not on the NAS host and not inside
  application images.
- One tagged Tailscale gateway advertises separate named Services for HTTPS and
  SSH.
- All user, administrator, inference, Grafana, and devbox access is
  tailnet-only.
- GPU nodes do not need Tailscale. They use a restricted NAS-LAN backend endpoint
  protected by route constraints, enrollment controls, and mTLS where identity
  already exists.
- The NAS has a DHCP reservation and local DNS names. GPU node DHCP reservations
  are recommended but are not correctness dependencies.
- There is no subnet scanner. Installed agents announce their own presence over
  the outbound channel.
- Everything required for the normal deployment starts with `docker compose up
  -d`; production components are not hidden behind opt-in profiles.

## Repository layout

The implementation should preserve `deploy/compose/` and add focused
subdirectories rather than introduce a competing top-level `docker/` tree:

```text
deploy/compose/
├── compose.yaml
├── .env.example
├── Caddyfile
├── tailscale/
│   ├── compose.yaml
│   ├── configure.sh
│   ├── grants.example.hujson
│   └── README.md
├── ai-devbox/
│   ├── compose.yaml
│   ├── Dockerfile
│   ├── entrypoint.sh
│   ├── sshd_config
│   └── authorized_keys.example
└── ... existing component directories
```

The exact Tailscale Service commands remain declarative in a checked-in
reconciler without credentials or tailnet-specific identities. The HTTPS
listener is expressed with an explicit `--https=443` flag because Services
configuration-file import cannot safely infer frontend TLS from an HTTP
upstream. The reconciler verifies the resulting Serve status before remaining
online.

## Network architecture

### Tailnet ingress

The Tailscale gateway publishes no Docker host port. It is the sole
human-facing ingress and joins only two new internal Docker networks:

- `tailnet-web-edge`, shared only with Caddy's internal web listener; and
- `tailnet-ssh-edge`, shared only with `ai-devbox`.

It does not join `data`, `application`, `agent-proxy`, `registry-edge`, or any
other private control-plane network.

The gateway advertises two separately authorized named Tailscale Services:

- a TCP/HTTPS service that terminates Tailscale-managed TLS and forwards to
  Caddy's internal web listener; and
- a raw TCP SSH service that forwards to `ai-devbox:22`, leaving OpenSSH
  encryption and authentication intact.

Caddy remains the HTTP policy and routing boundary after Tailscale. It applies
request-size limits, security headers, authentication, and routes to the
control API, LiteLLM, and Grafana. Neither LiteLLM nor Grafana becomes directly
reachable from the gateway.

```text
tailnet client
  -> named Tailscale HTTPS Service
  -> tailscale-gateway
  -> tailnet-web-edge
  -> Caddy
  -> control-api | LiteLLM | Grafana

tailnet SSH client
  -> named Tailscale SSH Service
  -> tailscale-gateway raw TCP forwarding
  -> tailnet-ssh-edge
  -> ai-devbox:22
```

### Restricted GPU node LAN ingress

The NAS receives one DHCP-reserved LAN address. Local DNS maps distinct names
such as the following to that address:

```text
enroll.vonk-forge.lan
agents.vonk-forge.lan
registry.vonk-forge.lan
```

Caddy exposes a dedicated backend TLS port bound specifically to the NAS LAN
address. The separate DNS names provide the TLS SNI split required because
client-certificate authentication cannot safely be conditional on an HTTP
path:

- enrollment allows only the bounded single enrollment route and uses a
  short-lived, single-use grant plus rate and body limits;
- agent traffic requires a verified node certificate and exposes only the
  agent API; and
- registry traffic requires agent mTLS and permits only the existing pull-only,
  digest-addressed operations.

The user-facing control hostname and inference routes do not listen on this
backend port. The NAS firewall additionally limits the port to configured GPU node
management CIDRs. No service uses host networking.

```text
GPU node
  -> backend DNS name:dedicated-port
  -> NAS_LAN_IP:dedicated-port
  -> Docker port forwarding
  -> Caddy backend listener
```

### NAS-to-GPU node egress

Caddy reaches LiteLLM by service name on their existing `ingress` network.
LiteLLM reaches the active GPU node model endpoint through the existing
non-internal `cluster-egress` bridge. Docker performs normal bridge routing and
source NAT through the NAS LAN interface.

```text
Caddy -> ingress -> LiteLLM:4000
LiteLLM -> cluster-egress -> GPU node management IP:model port
```

Tensor and direct-fabric traffic remains GPU node-to-GPU node and never passes
through the NAS.

## Stable identity without hard-coded GPU node addresses

Manual hardening and bootstrap remains a deliberate one-node operation using
the repository's scripts. It installs the pinned agent, stable control-plane
DNS names and trust anchor, and a one-time enrollment grant.

After installation, agent-driven presence replaces network discovery:

1. the agent initiates enrollment through the restricted LAN endpoint;
2. the manager records a pending enrollment with bounded hardware and host-key
   evidence;
3. an operator performs the existing physical identity comparison and approves
   the node;
4. the issued mTLS certificate binds the agent to one immutable `spk_` node ID;
5. subsequent heartbeats make the node automatically visible as online,
   offline, incompatible, revoked, or retired; and
6. Git remains authoritative for whether the node is accepted as a workload
   target.

The system does not scan the subnet, trust an SSH banner, automatically accept
a host key, install an agent, or add a detected machine to Git.

The management address is explicitly not identity. An authenticated heartbeat
may advertise candidate management addresses and model endpoints. The control
plane:

- selects only addresses within configured management CIDRs;
- rejects loopback, link-local, direct-fabric, tailnet, multicast, unspecified,
  broadcast, and otherwise unexpected addresses;
- associates the observation with the certificate-bound node ID;
- permits only workload-defined model ports and protocols;
- health-checks the candidate endpoint before publication; and
- withdraws the old route before validating a changed address.

Route authorization therefore changes from an exact, administratively
hard-coded URL allowlist to a policy over accepted node identity, configured
management CIDRs, declared workload ports, current agent evidence, and fresh
health. The generated LiteLLM configuration contains only the currently
accepted endpoint generation. A DHCP change does not require a Compose, fleet,
or model-profile edit.

DHCP reservations for GPU nodes remain recommended for troubleshooting and stable
operations. Changing a reservation does not change node identity.

## Tailscale identity, policy, and recovery

The gateway uses the official Tailscale image pinned by digest. It persists
state so ordinary restarts retain the same tailnet node identity. The initial
deployment uses Tailscale's default userspace networking because the gateway is
proxying explicit HTTPS and TCP Services rather than routing a subnet. It gets
no `/dev/net/tun`, `NET_ADMIN`, or `NET_RAW`. A later switch to kernel
networking requires measured need, a separate review, and explicit verification
of the minimum device and capability grant.

Unattended recovery uses a narrowly scoped OAuth client:

- client ID and secret are supplied through file-backed Compose secrets, never
  through `.env` or the repository;
- the client may create only the intended tagged gateway identity;
- the gateway requests a non-ephemeral identity and authenticates only when
  persisted state is absent or invalid; and
- `TS_AUTH_ONCE` or the current equivalent prevents unnecessary
  re-authentication.

The tailnet may continue to use GitHub as the human identity provider. That
interactive GitHub-backed login authorizes the operator to administer
Tailscale; it is not copied into the container. An authorized operator creates
the separate Tailscale OAuth client in the Tailscale admin console. No GitHub
access token or GitHub OAuth credential is stored in Compose or mounted into
the gateway.

The tailnet policy defines the two named Services, grants access independently
to web and SSH, and auto-approves only `tag:vonk-gateway` as a host for those
specific Services. This scoped `autoApprovers.services` rule is necessary for a
restored gateway to resume advertisements without manual approval. It must not
approve `svc:*` or grant the gateway broad device-management authority.

Loss or revocation of the OAuth credential prevents a new identity from being
created but does not invalidate already-persisted healthy state. Revocation of
the gateway node or its tag immediately removes tailnet ingress and never
causes a LAN fallback.

## AI devbox

### Runtime identity

`sshd` is the container's main supervised workload and starts as root because
it must bind port 22, create authenticated sessions, and switch credentials.
Compose uses `init: true`, so Docker's minimal init remains PID 1 and reaps
children. Every interactive session runs as `ai-dev` with a configurable
numeric UID and GID, defaulting to 1100.

The user has no password and no sudo implementation. OpenSSH permits only the
dedicated user and public-key authentication. Root login, passwords,
keyboard-interactive authentication, empty passwords, X11, SSH agent
forwarding, TCP forwarding, tunnels, gateway ports, and user-supplied
environment settings are disabled.

The container receives no Docker socket, host devices, privileged mode, host
networking, or `SYS_ADMIN`. It retains `no-new-privileges`. The implementation
does not start by dropping all capabilities because the root OpenSSH monitor
must create and switch to the unprivileged session; the exact required
capability behavior is verified in a running-container test.

### Filesystems and persistence

The image root filesystem is read-only. `/run`, `/tmp`, and `/var/tmp` are
bounded `tmpfs` mounts. Persistent state lives below one configurable NAS data
root and is never committed:

- home directory and user-installed tools;
- workspaces;
- package and build caches; and
- SSH host keys.

The operator's public `authorized_keys` source is an explicit external file
path. The repository contains only an example. Startup fails if the runtime
file is missing, empty, malformed, or unsafe, and installs it with correct
ownership and mode into the persistent home.

SSH host keys persist outside the immutable image. Rebuilding the image cannot
silently change the host identity seen by clients.

Mounting a persistent home hides files present at the image's `/home/ai-dev`
path. Image-supplied Rust, `uv`, and other bootstrap toolchains must therefore
live under stable system paths such as `/opt` or `/usr/local`, not only under
the image-layer home. Default shell and tmux configuration is stored as seed
material and copied only when its destination is absent. Startup never
overwrites user changes and never recursively changes ownership across an
existing workspace.

### Resources and reachability

The initial resource envelope remains four CPUs, an 8 GiB limit, a 4 GiB
reservation, and 2 GiB shared memory. These resources support builds, tests,
language tooling, and API-backed coding agents rather than local model
inference.

The devbox joins:

- `tailnet-ssh-edge` for inbound SSH from the gateway; and
- a dedicated ordinary egress network for package registries and model APIs.

It does not join any control-plane private network. It publishes no host port.

## Startup and lifecycle

All standard services are part of the same Compose project. Component files
are included for readability, not deployed as separate projects. Normal
startup remains:

```bash
docker compose up -d
```

Compose health and dependency conditions ensure that the gateway advertises a
route only when its local target is ready. Target failure makes the named
Service unhealthy or unavailable; it does not redirect traffic elsewhere.

The operator can still target one service for maintenance with normal Compose
commands, but `docker compose down` intentionally stops the complete NAS
application. Runbooks must warn that this ends active devbox SSH sessions as
well as control-plane and tailnet access.

## Failure handling

- A Tailscale outage removes human access without opening a LAN listener.
- Lost Tailscale state triggers scoped OAuth re-enrollment and service
  auto-approval; failure leaves ingress closed.
- An unavailable Caddy or devbox target withdraws or fails the corresponding
  named Service health check.
- Missing or invalid authorized keys stop the devbox rather than permit an
  alternate authentication method.
- Persisted SSH host-key loss is visible as a changed client fingerprint and is
  treated as a recovery event.
- A disconnected GPU node becomes offline after its bounded heartbeat deadline.
- A changed GPU node management address withdraws the prior inference route before
  validation of the replacement.
- An address outside configured management CIDRs, an undeclared model port, a
  stale health result, or a node absent from the accepted fleet cannot be
  published.
- Agent, registry, or enrollment backend failure pauses affected work and does
  not cause SSH or unauthenticated fallback.
- Existing workload and direct-fabric state on GPU nodes remains independent of a
  NAS restart, but shared administration and inference ingress is unavailable
  until the NAS stack recovers.

## Verification and acceptance

Automated structural tests render the complete Compose model and assert:

- the Tailscale and devbox services are included in the one project;
- no user-facing or SSH host ports are published;
- the only LAN publication is the explicit backend Caddy port bound to the
  configured NAS LAN address;
- the gateway joins only the two tailnet edge networks;
- the devbox joins only SSH edge and egress networks;
- Caddy, LiteLLM, PostgreSQL, Grafana, Prometheus, registry, and agents retain
  their intended network boundaries;
- secrets use file inputs and no real credential or public key is checked in;
- images that are pulled are digest pinned; and
- read-only roots, bounded temporary filesystems, logging, health checks, and
  restart behavior meet the service-host policy.

Container tests verify:

- the devbox image builds and `sshd -t` succeeds;
- a valid key logs in only as `ai-dev`;
- root, password, keyboard-interactive, forwarding, tunneling, and empty-key
  paths fail;
- `sudo` is absent and the session cannot gain privileges;
- the root filesystem is immutable while intended persistent paths remain
  writable;
- image bootstrap tools remain available when an empty persistent home is
  mounted;
- default configuration is seeded once and user changes survive restart;
- host keys and user state survive rebuilds; and
- missing keys fail startup.

Routing and control tests verify:

- an accepted mTLS agent automatically appears without a subnet scan;
- an unapproved or Git-absent node cannot receive routine work or inference
  routes;
- node identity remains stable across a management-address change;
- the old address is withdrawn before the new address is probed;
- invalid CIDRs, interface classes, ports, protocols, stale evidence, and
  unhealthy endpoints are rejected;
- generated LiteLLM routes contain only accepted current endpoints; and
- Caddy reaches LiteLLM internally while LiteLLM reaches a simulated GPU node only
  through `cluster-egress`.

Deployment acceptance on the NAS and tailnet verifies:

- authorized tailnet users can reach the HTTPS Service;
- only authorized identities can reach the SSH Service;
- an ordinary LAN client cannot reach user, inference, Grafana, or devbox
  endpoints;
- a GPU node-subnet client with the correct mTLS identity can reach only its
  backend routes;
- wrong, revoked, expired, and absent client certificates fail;
- the NAS firewall rejects backend connections outside the allowed management
  CIDRs;
- Tailscale state loss recovers unattended through the scoped OAuth client and
  specific service auto-approvals; and
- backup and restore preserves Tailscale identity, devbox state, and SSH host
  identity.

## Documentation and operator inputs

The implementation updates the control-plane bootstrap and recovery runbooks
and adds focused Tailscale and devbox runbooks. `.env.example` documents only
non-secret inputs such as:

- reserved NAS LAN bind address;
- backend port;
- local DNS names;
- allowed GPU node management CIDRs;
- devbox UID, GID, data root, and authorized-keys file path; and
- secret-file paths for the Tailscale OAuth client.

Tailnet-specific grants, service definitions, auto-approvals, and access tests
are provided as placeholders/examples. Real OAuth credentials, tailnet IDs,
personal public keys, LAN addresses, and DNS names remain host-local.

## Scope boundaries

- This design does not move model serving, model weights, or tensor traffic to
  the NAS.
- It does not install Tailscale on the GPU nodes.
- It does not introduce LAN subnet scanning, mDNS trust, automatic SSH host-key
  acceptance, or automatic node onboarding.
- It does not make a DHCP address part of immutable node identity.
- It does not expose Docker, the Docker socket, or control-plane private
  networks to the devbox.
- It does not provide a LAN fallback for human access.
- It does not automate tailnet policy mutation from the running gateway; policy
  remains administrator-controlled and reviewable.
- It does not claim physical NAS, tailnet, firewall, DNS, or GPU node acceptance
  from simulator-only tests.
