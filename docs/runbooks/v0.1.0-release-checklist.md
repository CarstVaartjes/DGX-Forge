# DGX-Forge v0.1.0 release checklist

This is the authoritative order-of-operations ledger for the first real
DGX-Forge release. Do not reorder steps, treat a simulated report as physical
evidence, or continue past a failed stop condition.

## Current state

- Pull request [#29](https://github.com/CarstVaartjes/DGX-Forge/pull/29)
  contains the release-readiness implementation and is not merged.
- There is no signed or installable DGX-Forge release.
- Public manually uploaded `0.1.0` API, worker, and Hermes versions are
  disposable candidates, not release artifacts.
- The repository ships the delegated authority client and contract, but no
  authority server implementation or deployment.
- The release verifier reports six open physical gates. The approved physical
  exporter and a staged candidate workflow capable of closing them do not yet
  exist.

Run this at any point for the machine-readable state:

```bash
scripts/verify-platform-release --candidate 0.1.0 --json
```

An exit status of `2` means blocked. Do not suppress it.

## Roles

| Role | Responsibility |
| --- | --- |
| Repository maintainer | PR checks, merge, exact tag, and GitHub Release inspection. |
| Authority administrator | Separately deploys and accepts the delegated TUF service and protected GitHub environment. |
| Physical acceptance operator | Exercises real hardware and recovery paths without holding the physical evidence signing key. |
| Physical acceptance approver | Independently reviews sanitized detail digests and signs through the approved exporter. |
| Control-host administrator | Makes packages public, installs the signed NAS generation, and onboards Sparks. |

One person may hold multiple small-cluster roles, but private authorities,
physical observations, and release approval remain separate credentials and
audit events.

## Phase 1: Merge release readiness

Owner: repository maintainer.

1. Wait until GitHub reports Actions operational.
2. Inspect the exact PR head and checks:

   ```bash
   gh pr view 29 --json headRefOid,isDraft,mergeStateStatus,statusCheckRollup
   gh pr checks 29 --watch --interval 10
   ```

3. Require successful `Ruff`, `Generated control clients`, and
   `PR contract smoke` checks on the current head.
4. Merge without an administrator bypass:

   ```bash
   gh pr merge 29 --merge
   ```

If the Actions incident dropped the original webhook and no run exists, close
and reopen the PR once after GitHub reports recovery. `reopened` is a normal
`pull_request` trigger for this workflow:

```bash
gh pr close 29
gh pr reopen 29
gh pr checks 29 --watch --interval 10
```

Stop if the head SHA changes unexpectedly, a required check is absent or
fails, Actions remains degraded, the PR has a merge conflict, or merging would
use a ruleset bypass. Do not create empty commits repeatedly to chase a
throttled webhook.

Evidence: PR URL, exact head SHA, merge SHA, and three successful check URLs.

## Phase 2: Close implementation blockers

These are product prerequisites, not operator paperwork.

### Delegated platform authority

Follow [Delegated platform authority deployment](platform-authority-deployment.md).
The phase is blocked until a reviewed server implementation is deployed and
its positive and negative GitHub OIDC acceptance passes. Do not enable either
release variable before that acceptance.

Evidence: server image/source identity, deployment digest, TLS identity,
offline-root/delegation record, backup/restore result, OIDC policy result, and
one sanitized append-only target/channel acceptance report.

### Physical candidate and evidence path

Follow [Physical v0.1.0 release acceptance](physical-release-acceptance.md).
The current tag workflow cannot both create the exact protected candidate and
require its physical evidence before final publication. The approved exporter
for all six gates is also incomplete. A reviewed staged-candidate/finalization
workflow and exporter/verifier binding must land before this phase can close.

Evidence: one candidate/release/run-bound physical report, every required
signed envelope or equivalent verifier-bound report, and a final release
verifier result with `status: passed`.

Stop while either implementation is absent. Never solve the ordering gap by
promoting workstation-built bytes, editing `remaining_release_gates`, or
publishing `stable` before acceptance.

## Phase 3: Configure protected publication

Owner: authority administrator. Perform only after Phase 2 passes.

1. Configure the protected `platform-release` GitHub environment and the exact
   authority URL/audience as described in the authority runbook.
2. Enable both default-off repository variables:

   ```bash
   gh variable set DGX_CONTAINER_RELEASES_ENABLED --body true
   gh variable set DGX_PLATFORM_RELEASES_ENABLED --body true
   gh variable list
   ```

3. Rerun the release verifier with the root-owned physical acceptance public
   document. Require exit status `0` and `status: passed`:

   ```bash
   sudo scripts/verify-platform-release \
     --candidate 0.1.0 \
     --physical-evidence-public-key \
       /srv/dgx-forge/trust/physical-acceptance-public.json \
     --json
   ```

Stop if either variable was enabled early, the protected environment lacks its
review policy, or the verifier is blocked.

Evidence: reviewed environment policy, variable listing, authority acceptance,
physical key ID, and passing release-verifier digest.

## Phase 4: Remove only disposable candidates

Owner: repository maintainer. Perform immediately before tagging, in the same
release window. GitHub package deletion requires package-admin access and an
appropriately scoped credential.

First list the exact versions and record the IDs whose tag list contains
`0.1.0`:

```bash
for package in dgx-forge-api dgx-forge-worker dgx-forge-hermes; do
  gh api --paginate \
    "/user/packages/container/${package}/versions?per_page=100" \
    --jq '.[] | select(.metadata.container.tags | index("0.1.0")) | {id,name,tags:.metadata.container.tags}'
done
```

Require exactly one reviewed version ID for each package and no unexpected
tag that must be retained. Set each numeric ID explicitly, validate it, then
delete only that version:

```bash
read -r -p "Reviewed dgx-forge-api candidate version ID: " \
  api_candidate_version_id
read -r -p "Reviewed dgx-forge-worker candidate version ID: " \
  worker_candidate_version_id
read -r -p "Reviewed dgx-forge-hermes candidate version ID: " \
  hermes_candidate_version_id
for candidate_id in \
  "$api_candidate_version_id" \
  "$worker_candidate_version_id" \
  "$hermes_candidate_version_id"; do
  case "$candidate_id" in
    ''|*[!0-9]*) echo "candidate version ID is not numeric" >&2; exit 64 ;;
  esac
done
gh api --method DELETE \
  "/user/packages/container/dgx-forge-api/versions/${api_candidate_version_id}"
gh api --method DELETE \
  "/user/packages/container/dgx-forge-worker/versions/${worker_candidate_version_id}"
gh api --method DELETE \
  "/user/packages/container/dgx-forge-hermes/versions/${hermes_candidate_version_id}"
```

Confirm the version is absent from all six repositories:

```bash
scripts/refuse-existing-image-version 0.1.0 \
  ghcr.io/carstvaartjes/dgx-forge-api \
  ghcr.io/carstvaartjes/dgx-forge-worker \
  ghcr.io/carstvaartjes/dgx-forge-hermes \
  ghcr.io/carstvaartjes/dgx-forge-agent \
  ghcr.io/carstvaartjes/dgx-forge-agent-supervisor \
  ghcr.io/carstvaartjes/dgx-forge-tooling
```

Stop if more than one version matches, a matching version carries a tag that
must survive, a delete request fails, or any repository still resolves
`0.1.0`. Do not delete the package itself, `staging`, `latest`, or an unrelated
version.

Evidence: pre-delete version records, three deletion responses/audit events,
and the successful six-repository absence check.

## Phase 5: Create the immutable tag

Owner: repository maintainer.

```bash
test -z "$(git status --porcelain)"
git fetch --prune origin main --tags
release_commit=$(gh pr view 29 --json mergeCommit,state \
  --jq 'select(.state == "MERGED") | .mergeCommit.oid')
test -n "$release_commit"
git merge-base --is-ancestor "$release_commit" origin/main
test -z "$(git ls-remote --tags origin \
  refs/tags/v0.1.0 'refs/tags/v0.1.0^{}')"
git tag -s v0.1.0 "$release_commit" -m "DGX-Forge v0.1.0"
git show --show-signature --no-patch v0.1.0
git push origin v0.1.0
```

Stop if the PR is not merged into `origin/main`, the worktree is dirty,
signature verification fails, a `v0.1.0` tag already exists locally or
remotely, or any Phase 1–4 evidence changed. Never move or recreate the tag.

Evidence: tag object, signature, commit SHA, and push result.

## Phase 6: Require the complete protected chain

Owner: repository maintainer and authority administrator.

```bash
tag_run_id=$(gh run list --workflow CI --limit 20 \
  --json databaseId,headBranch,status,conclusion,url,headSha \
  --jq '[.[] | select(.headBranch == "v0.1.0")][0].databaseId')
case "$tag_run_id" in
  ''|null|*[!0-9]*) echo "exact v0.1.0 CI run is unavailable" >&2; exit 1 ;;
esac
gh run watch "$tag_run_id" --exit-status
gh release view v0.1.0 --json url,tagName,targetCommitish,assets
```

Require the six-artifact publication evidence, deployment bundle, host-updater
attestation, immutable TUF target receipt, `stable` channel receipt, and final
GitHub Release. Verify every digest using
[Platform release publication](platform-release-publication.md).

Stop on a partial package set, mismatched receipt, missing attestation,
authority rejection, missing release asset, or non-successful job. Preserve
evidence and retry only byte-identical idempotent operations; do not retag.

## Phase 7: Make packages public and install

Owner: control-host administrator.

For each of the six GHCR packages, open its GitHub package settings and choose
**Danger Zone → Change visibility → Set package visibility to Public**. Confirm
anonymous manifest access. Do not add a GitHub token to NAS configuration.

Then follow, in order:

1. [Docker control-host deployment](../../deploy/compose/README.md) to install
   the TUF-authorized generation on the NAS/control host.
2. [Spark agent PKI](agent-pki.md) to establish the cluster authority.
3. [Add a DGX Spark node](node-onboarding.md) once per Spark, with no fixed
   fleet size.
4. [Platform release update](platform-release-update.md) for signed agent
   rollout and rollback verification.

Stop if anonymous package access fails, the selected target is not authorized,
the host updater attestation fails, or a Spark requires SSH for the standard
update path.

Evidence: public package probes, selected generation receipt, healthy control
services, accepted node identities, exact active Spark agent digest, and final
model/routing probes.
